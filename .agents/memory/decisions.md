# 架构决策记录

每条记一件事：**当时有哪些选项、为什么选了这个、付出了什么代价**。想推翻某个设计之前先读对应条目。

---

## ADR-1 不让 AstrBot 学文档，而是给它工具去问 Karin

**背景**：最初诉求是「让 AstrBot 知道 Karin 框架的内容以及插件的使用方法」。

| 方案 | 结果 |
| --- | --- |
| 把 Karin 文档塞进 system prompt | 文档会过期；第三方插件文档根本不存在；每轮都付费 |
| 往 Karin 插件目录写说明文件让 AstrBot 读 | 要求同机同文件系统；「使用方法」仍要人工维护 |
| **给模型一组工具，现场查** | 数据永远最新，只在用时付费 |

**代价**：工具描述本身占每轮固定开销（见 ADR-6）。

---

## ADR-2 直接调 Karin 进程内的插件函数，不走 QQ 消息

| 方案 | 结果 |
| --- | --- |
| 让 AstrBot 通过 QQ 发消息给 Karin 的 bot | 绕一圈，还依赖特定插件做中继 |
| 伪造 OneBot 事件喂进适配器 | 会被当成真实消息参与统计、风控，还要维护完整结构 |
| **在 Karin 进程内直接调用插件函数** | 最短路径，但要复刻框架的调用链 |

用户明确否决了前两种（不依赖中继插件、不借助 OneBot）。
**代价**：依赖框架内部模块（见 bridge 的 ADR-2），且插件不是真实事件，部分插件跑不通。

---

## ADR-3 六个细粒度工具，而不是一个 `karin(action, payload)` 万能工具

| 方案 | 结果 |
| --- | --- |
| 单个万能工具 | 省 token；但模型要自己拼 JSON payload，参数名全靠记忆，错误率高 |
| **六个专用工具** | 每个参数都有类型与描述，模型照着填就行；固定开销更大 |

**代价**：约 700–900 token/轮的固定成本（后来加到七个工具，约 800–1000）。
这是为「模型真的会用它」付的钱。

---

## ADR-4 `karin_call` 的 `text` 用 `sample` 作为约定

指令以正则注册，模型不知道该把 `text` 填成什么。bridge 从正则反推 `sample`，
工具输出里直接写「调用时 text 填：<sample>」。

**代价**：反推不完美时模型会填错；好在 `call` 失败会返回候选指令名，模型能自我修正一次。

---

## ADR-5 `enabled` 开关 + 全链路截断

用户问「会不会每次都调 API 太耗 token」。事实：不轮询、不监听，只有主动调用才请求；
但 schema 每轮注入是固定开销，且工具返回值会永久留在上下文里反复计费。

**决定**：`enabled` 总开关 + 所有返回文本过 `_clip` + `deliver` 时正文不回传。

**代价**：截断意味着模型可能拿不到完整数据，需要用户改用 `deliver` 或缩小查询范围。
宁可让模型要两次，也不要一次塞爆上下文。

---

## ADR-6 `karin_search` 作为第六个工具

用户说记不住插件指令，但希望保留指令能力；模型又不能背一张表。

| 方案 | 结果 |
| --- | --- |
| 让用户每次手打指令 | 违背「让 AstrBot 自主操作」的初衷 |
| 把所有指令写进 system prompt | 上下文爆炸，且更新即失效 |
| **加一个模糊检索工具** | 按需查，只带回 10 条 |

`karin_commands` 负责「已知插件名」，`karin_search` 负责「不知道」。
**代价**：再 +1 个 schema 的开销；效果取决于 bridge 侧 haystack 的构建。

---

## ADR-7 `karin_share` 只交出链接，不取回解析结果

| 方案 | 结果 |
| --- | --- |
| 用 `karin_call` 调 kkk 的解析指令，把结果当文本回给 AstrBot | kkk 产出的是消息元素（图片/视频卡片），不是结构化数据；转文本会丢内容，还占大量上下文 |
| **新增 `karin_share`，强制 `deliver`，只回一句确认** | 卡片原样发到目标会话，AstrBot 不需要理解它 |

**代价**：AstrBot 不知道解析成功与否（只知道「已交给插件」），失败要靠 `karin_logs`；
平台白名单只有 bridge 侧的 `LINK_USE_CASES`（现为 bilibili / douyin），扩平台必须改 bridge。

---

## ADR-8 `usecase` 由 bridge 判断，AstrBot 只透传空串

| 方案 | 结果 |
| --- | --- |
| 在 `main.py` 里也写一份域名正则做预判 | 两份正则必然漂移，模型看到的还是 Python 的判断 |
| **`usecase` 留空，bridge 按链接 `inferUseCase`** | 判据只有一处；短链判断不出来时模型仍可显式指定 |

**代价**：docstring 得说清「一般留空」，否则模型可能瞎填；填错时 bridge 报错里会带上可用用例，模型能自我纠正。

---

## ADR-9 投递对象 = 消息所在的会话，不是提问的人

初版缺省是 `('group', group_id)`。中途曾按「谁问发给谁」改成发送者优先（群聊也私发给发言人），
被用户否决（m01050）——AstrBot 的文字回复本来就回到提问处，卡片也该回到同一个会话。

| 方案 | 结果 |
| --- | --- |
| **群聊发回群、私聊发回本人** | 和文字回复落在同一处，行为可预期 |
| 一律发给发送者（群聊也私发） | 群里提问、卡片只在自己私聊出现，看着像没发出去；还要求发言人与机器人是好友 |

**决定**：`_resolve_scene` 顺序 = `target 显式（+scene）` → `scene 显式` → `group_id`（group）→ `sender_id`（friend）→ 空（报错）。
只给 `target` 时按当前消息判断它是群号还是 QQ 号。

**代价**：发到别处必须显式传 `scene`+`target`；AstrBot 接非 QQ 平台（Telegram 等）时拿到的 ID 在 Karin 侧不存在。

## ADR-10 卡片由 `on_decorating_result` 自动补发，不再依赖模型主动调 `karin_share`

**背景**：真机实测（2026-11-09）发现，只有明确说「触发一下 kkk 解析」时模型才调 `karin_share`；
正常聊到一条视频时它只把链接写进回复。用户诉求是「自动去调用，别让我主动提」。

只改 docstring 不够：`karin_share` 是第七个工具，docstring 再长也只是**建议**，
而且模型要为此多跑一整轮（决定调用 → 等 HTTP → 再组织回复）。

| 方案 | 结果 |
| --- | --- |
| 继续加强 docstring | 有改善但不保证；每次多一轮上下文，随模型波动 |
| 插件用本地正则挑链接自动 POST | 判定确定、零 LLM 调用；但**只能按位置猜**哪条是「选中」的 |
| **模型在回复末尾写 `[[share:<链接>]]`，插件读走并替换成链接** | 选哪条由模型决定；仍只有一轮回复，零额外工具调用 |
| 用 `@filter.command` 注册显式指令 | 又回到「要用户主动提」，与诉求相反 |

初版实现是「从正文里取第一条链接」，被用户否决（m04505）：
「这里的取用的链接要的是 astrbot 筛选后发给我的链接」——正文里常列 5 条候选、只有一条是真推荐的，
按位置取必然取错，而且错得很安静。

**现行实现**：`_auto_share` 挂 `on_decorating_result`，条件 `result.is_llm_result()`；
`SHARE_TAG = re.compile(r"\[\[\s*share\s*:\s*([^\]]+?)\s*\]\]", re.I)` 在 `get_plain_text()` 里找标记；
命中先 `_strip_share_tag` 把标记换成普通链接（标记绝不外泄），再 `_normalize_link` 校验，
最后交给 `_deliver_share`（后台任务），缺省 `scene/target` 走 `_resolve_scene`。失败只写日志。

**真机修正史（都是踩出来的，别再改回去）**

1. **`auto_share` 必须写进 `_conf_schema.json`**。只写 `getattr(self.config, "auto_share", True)` 时，
   配置对象上有同名属性但值为 `None`，默认值不生效——日志出现「自动补卡片=关」，且 `[[share:...]]` 原样漏给用户。
   修法：补进 schema + `_auto_share_on()` 统一判定。
2. **标记是替换不是删除**。纯删除会让用户只剩一段没有链接的正文（用户原话：「卡片是有了 但是没给我链接啊」）。
   现在 `_strip_share_tag(result, link)` 把标记换成完整链接；文案别处已贴过同一条链接时只删除、不重复。
3. **解析必须后台跑**。原来 `await self._post("share", …)` 堵在 `on_decorating_result` 里，
   kkk 出卡片 10~14 秒，正文一直发不出去；超时后还把「（卡片没发出来：…）」追加进正文。
   而且 kkk 先发卡片再返回，所以卡片会抢在正文前面到达。现在 `create_task` + `self._bg_tasks`。
4. **`timeout` 20 → 60**（`_conf_schema.json`、`_post`、`_probe` 三处对齐；此前代码默认 30、提示文案写 20）。
5. **成功路径不打日志**，只有失败才 `logger.warning`——每轮刷一行纯噪音。

**代价**：用户不再能从正文得知「卡片失败了」，失败只留在 AstrBot 日志里（用户明确说只想要卡片，不想看报错）。

## ADR-11 格式提示按需注入：不装 skill 也要能出卡片

**触发事实**：真机私聊「发个视频」全链通了，但那条链路**完全是 skill（`fixed-reply-format`）撑起来的**，
它规定「观后两三句 → 链接单独一条纯 URL → `karin_share`」，`[[share:]]` 标记根本没参与。
skill 是用户自己装的，换机器 / 换会话就没了。

| 方案 | 结果 |
| --- | --- |
| 只靠 skill | 换机器就没卡片；插件完全被动 |
| 每轮都写进系统提示 | 稳定，但所有闲聊多付一份 token（约 60 token/轮） |
| **按消息触发注入** | 只有「像是要视频」那轮才付；闲聊零开销 |
| 正文里正则取第一条链接 | ADR-10 已否决 |

**决定**：`_hint_share_format`（`on_llm_request`）在 `HINT_TRIGGER` 命中时把 `SHARE_HINT` 追加到 `req.system_prompt`，
由 `prompt_hint` 控制。只改这一个字段：不发请求、不调模型、不动用户消息；已有 `[[share:` 就不重复加。
`HINT_TRIGGER` 现覆盖：视频 / 短片 / 剪辑 / 下一个 / 再来 / 来一支 / 来一个 / 看看 / 发个 / BV 号 / b23.tv / bilibili.com / douyin.com。

**代价**：兜底是否生效取决于 `HINT_TRIGGER` 有没有覆盖用户的实际说法——漏了就是「没卡片，也看不出为什么」。

**追加：提示词不够，必须再有本地兜底**。让模型「随便给我一条 B站视频看看」，它调了别的工具、
最后输出「正文两句 + 单独一条链接」，**既不调 `karin_share` 也不写标记**，12 秒内 Karin 没有 `action=share`。
于是 `_auto_share` 改成两层：有标记认标记；没标记取 `_all_links` 的结果。

**同日再改：从「唯一链接」到「每条都发」（用户 m06356）**

先是只认「全篇恰好一条链接」（`_sole_link`），依据是「唯一即确定」——被否决的从来是「5 条里取第一条」，
不是「只有一条时取那一条」。用户随后否决了这个保守设定：

> 要 因为有时候 astrbot 莫名其妙会多给链接 有时候只给一条 就是那个 我会自己刷 b 站的插件

也就是说「两条以上就放弃」不符合真实使用：AstrBot 有时给一条、有时给三四条，
用户要的是**给几条就补几张卡**——「链接进了会话就变成卡片」，不是「插件替我挑一条」。
`_sole_link` 因此换成 `_all_links`（按出现顺序收集并去重），每条各 `create_task` 一个 `_deliver_share`；
新增 `MAX_AUTO_LINKS = 5`，超了只发前 5 条并写 warning（每条要渲染 2~3 MB 的图，不封顶会把 puppeteer 和聊天窗一起拖死）。

**两个必须记住的实现细节**

- **去重靠区间覆盖**：一条链接本身含 BV 号（`https://www.bilibili.com/video/BV1xx`），
  不先用 `MEDIA_LINK` 的区间盖掉 `MEDIA_ID` 的命中，就会数成两条、补两张一模一样的图。
- **`_normalize_link` 用一条正则剥首尾标点**：分两步剥（先引号后逗号）时，
  模型把链接贴成 Python 列表（`…BV1xx',`）会留下 `…BV1xx'` 这种尾巴。

**代价**：正文里顺口提一条 B站/抖音链接也会触发一次渲染（数秒 + 数 MB）。要关就设 `auto_share=false`。

## 已知偏差（记着，暂不改）

`main.py` 里 `karin_share` 的 docstring（约 :357）还写着「正文里出现链接本身**不会**触发卡片——
只有 `[[share:...]]` 里那一条会」。前半句与 ADR-11 冲突：没标记时 `_auto_share` 会为正文里
**每条**链接各补一张卡（上限 `MAX_AUTO_LINKS = 5`），有标记时才只发标记那一条。

2026-11-11 决定**先不改**（用户确认）：日常路径（写标记 → 只发那一条）说明书与实现一致，
错的那半句只在「不想出卡」时才有意义；而改成「不写标记也出卡」可能让模型偷懒不点名，
反而一次弹多张。**下次动这个插件时顺手一起改**，改完必须重新上传插件才生效（改的是 prompt，不是逻辑）。
